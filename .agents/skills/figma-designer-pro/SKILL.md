# Figmaの制作データを整える

指定された実データ、関連する親・正本、案件で合意した仕様を根拠にする。ファイル指定なら現行の制作ページを特定し、保管・検証用の複製は集計から外す。対象を取得できず別候補で結果が変わるときは確認する。新規制作では次に差し替える文章・画像を含む代表画面を起点にする。Webの品質監査、不足ページの判定、サイトマップ作成、要件ヒアリングは別の仕事として扱う。

## 初回の判断

各セクションで「文章を伸ばす」「記事を入れ替える」「見出しを一括変更する」など、次の編集操作を具体化する。同じ役割の文字・色・余白・部品を入れ子やインスタンス内も含めて横断し、値が少し違うものも比較に入れる。各候補で **今そろえる属性** と **次回から連動させる範囲** を別々に決める。

| 提案 | 判断する根拠 | 初回に見せるもの |
| --- | --- | --- |
| 値をそろえる | 同じ役割・状態で比較でき、差を解消する利点がある。将来の一括変更を要する根拠はない。 | 実物、値の分布、推奨値、動く箇所。個別の値や親の間隔を直す。 |
| 一緒に更新する | 複数の使用先に同じ変更を届けたい。正本の複製数と独立した使用場面を区別する。 | 変更元と届く先、文言や写真など各箇所で変えられる部分。既存の親・部品で届くならそこまで。別の部品や画面をまたぐ属性に限り、既存のスタイル・変数を検討し、適切な定義がなければ新設を提案する。 |
| 個別に残す | 手詰め、強調、状態、異なる読み順など、別々に調整する理由がある。 | 代表例と、一括変更すると失われる表現や編集の自由。単発で再利用先が見つからなければ個別書式で十分。 |

優先する根拠は合意済みの仕様、正本と使用先、同じ状態の実測の順。頻度や値の近さだけで意図を確定しない。両案が成り立つときは「要確認」として現状と案を並べ、「次に○○を変えたら、ここにも反映しますか？」など答えで処置が決まる一問にする。該当例のない分類は省く。

## 初回の提案と可視化

1. 役割の反復、写真と本文の親子関係、自由配置、文字枠と字形、同型項目内の間隔・共通列の端を実測する。枠の越境と小数は[検査基準の該当節](references/data-checks.md)と同梱の検査関数を使う。取得できない属性・範囲は未確認とする。
2. 整理・修正を一任されたら[指摘の見せ方](references/feedback.md)に従い、制作画面の外に実物付きの比較を作ってリンクする。チャットにも選べる番号、対象、変更前後、編集・表示への影響を載せる。「点検して」「報告だけ」、対象だけの共有、書き込み不可の場合は、チャットに実例と対象リンクを返す。
3. 見た目や共通定義が変わる案は初回から示し、承認を待つ。番号で選べるようにし、「すべて」はチャットに列挙した案を指す。具体的な修正指示はその範囲の承認として扱う。途中で新しい表示変更が必要になれば追加提案にする。

## 制作・反映・引き継ぎ

承認後は対象と変更するローカル正本の編集前バックアップを取り、別ID・親・寸法・表示・参照を読み戻す。通常は別の作業コピーに反映する。共有正本・スタイルの変更が原本やバックアップへ波及する場合は参照を独立させ、復元できない枝は保留する。原本への直接反映には反映先の明示が必要。

文章や画像は一緒に選ぶ単位でまとめ、通常の並びは親の間隔で調整し、図版の自由配置を保つ。対象に応じて[構造・文字・色の基準](references/data-checks.md)の該当節を使う。[編集操作の試験](references/deep-review.md#整理後の編集操作の試験)で、文量変更・並べ替え・一括更新など提案した操作を作業用の複製で確かめる。試験後は実際の結果を再取得し、承認した表示差、越境・間隔・小数、正本と上書きを照合する。完了時は修正結果、バックアップ、比較資料へのリンクと、できるようになった操作・例外・未検証を短く伝える。

納品・他担当への引き継ぎを頼まれた場合は[引き継ぎ資料](references/handoff.md)を使う。
