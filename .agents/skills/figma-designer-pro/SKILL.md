# Figmaの制作データを整える

GitHubの配布リポジトリURLからの依頼では、作業前にリモートの `refs/heads/main` を解決する（例：`git ls-remote https://github.com/yoshio-1126/yoshio-1126-codex-skills.git refs/heads/main`）。取得したコミットのツリーからこの本文と必要な参照資料・検査コードを読み、全て同じ版で進める。最初に `raw/.../main/...` で開いた本文は古い場合があるため、その取得だけで最新版とは判定しない。コミットやタグを利用者が指定したときはその版を使う。

指定された実データ、関連する親・正本、案件で合意した仕様を根拠にする。ファイル指定なら現行の制作ページを特定し、保管・検証用の複製は集計から外す。対象を取得できず別候補で結果が変わるときは確認する。新規制作では次に差し替える文章・画像を含む代表画面を起点にする。Webの品質監査、不足ページの判定、サイトマップ作成、要件ヒアリングは別の仕事として扱う。

## 初回の点検と返答

指定範囲で次を確認する。報告の短さを理由に、検査や独立した指摘を省かない。

- **構造・表示**　一緒に動かす写真と説明の親子関係、文章が増えたときの枠の追従、文字のはみ出し、部品の参照先を実物で確かめる。同じ位置の背景・線・画像は、重なった兄弟とその中身を比較し、同じ内容を二重に編集する状態を拾う。枠だけが出ている場合は、その状態を正確に書く。写真は全使用先で塗り配列も調べ、同じ枠に複数の画像塗りが残り差し替えを妨げる箇所を把握する。
- **情報のまとまり**　セクション内の各ブロックでも、何の見出しか、本文・関連リンクがどこまで続くかを読む。左の見出しと右の説明が独立する箇所は、それぞれを同じ横並びの親の子にする。右側の開始位置が低くても縦積みとは限らない。見出しの外枠まで内容幅にし、右列との余白は2列を持つ親のgapにする。並ぶ実要素の端で測り、語句を替えたときも間隔が保たれるかを確認する。[意味構造と読み順](references/data-checks.md#htmlの意味構造と読み順)を参照。
- **文字枠**　短い見出し・リンク・ラベルは上限なしの内容幅。長い本文は親の内幅に合わせて折り返し、高さを自動にする。文字位置は親の余白・間隔・整列で決める。残り幅を使う本文列とそこまでのラッパーは横を「コンテナに合わせて拡大」(Fill) にし、位置合わせの固定幅を外す。可変幅を決める外側のセクションから幅を変え、写真・見出し・余白を引いた増減分が本文まで届くことを実測する。[文字幅と折り返しの確認](references/data-checks.md#文字幅と折り返し)を使う。
- **配置の小数**　基準幅で[整数寸法の検査](references/data-checks.md#整数寸法の全件検査)を行う。配置枠の座標・幅・高さ・間隔の端数は、表示が崩れていなくても対象。中央揃えなど親子の寸法から生じた場合はその原因を押さえ、図版の輪郭・回転・計算誤差は除く。
- **繰り返す情報・デザイン**　初回の承認を求める前に、対象全体を見て、カード・工程・ナビなど反復するまとまりを役割別に列挙する。別の小見出しの下や別の親に分かれていても、同じ見せ方なら比較に含める。各まとまりについて全件数と実測数を突き合わせ、図・写真の端から対応する名前や説明の端までの間隔を同じ二辺で測る。外れ値は意図的な差かを判断し、見えるズレは初回の提案に出す。[反復項目の全件比較](references/data-checks.md#反復項目の全件比較)を使う。　レイヤー名や部品化の有無にかかわらず、同じ情報を同じ順序で見せる全項目を一組として調べる。写真＋説明のカードなら、全件で写真枠・本文列の幅と高さ、列間、上下左右の内余白、見出しから本文までの間隔を同じ辺から測る。文量の差と、同じ役割なのに個別の数値で位置を合わせている差を分ける。中央揃えなら上下の余白、上揃えなら上端など、全件に一つの配置ルールが通るか確かめる。グループ化と数値のばらつきは別の指摘にする。

一任された整理では、初回にデザイナーの判断が要る箇所と、実際の見た目を変える提案を、それぞれ「場所＋何を確認・調整するか」で短く伝える。必要な承認を一度だけ尋ねる。構造・設定だけの整理も内部で点検し、見た目への影響がなければ個別のミスとして並べない。構造の整理だけが必要で承認前なら「見た目を保ってデータを整理できます。進めてもよいですか？」と確認する。構造を明示して質問された場合はその範囲で答える。点検・報告のみの依頼では修正を尋ねない。

承認された調整と、依頼された範囲の構造整理を反映する。具体的な修正指示は再確認せず進める。見た目の意図や指定外の影響先が決められない箇所だけは、反映前に確認する。

## 制作・反映・引き継ぎ

承認後は原本を修正前の基準として保持し、独立したコピーへ反映する。原本が使う正本やスタイルに変更が波及しないことを確認する。同じ構造を反復する項目は、共通の親設定やカード正本で寸法・余白・整列を管理し、写真と文言は個別に差し替えられるようにする。コンポーネントを設けるのは、独立した複数の使用先で同じ変更を一度で届ける用途があり、既存の親や書式で足りないとき。親のフッターで更新できる文字だけのナビ項目は通常のテキストかフレームにする。原本保護のためコピーした部品にも同じ判断を適用する。原本への直接編集を明示された場合は、先に復元手段を確保する。

文章や画像は一緒に選ぶ単位でまとめ、通常の並びは親の間隔で調整し、図版の自由配置を保つ。対象に応じて[構造・文字・色の基準](references/data-checks.md)の該当節を使う。[編集操作の試験](references/deep-review.md#整理後の編集操作の試験)で、文量変更・並べ替え・一括更新など提案した操作を作業用の複製で確かめる。試験後は実際の結果を再取得し、承認した表示差、越境・間隔・小数、正本と上書きを照合する。繰り返しは全件の寸法と配置ルールを再測定する。共通部品は各使用先で、変更対象外の文字・アイコンの実効色と背景の組み合わせを原本と照合し、反転色などの固有設定を保つ。重複を統合した箇所は残数と表示を確認する。[確認用ページの配置](references/feedback.md)に従い、画面全体は「オリジナル」と「修正版」の2フレームにする。修正版の注釈は、デザイン上の確認事項と実際に見た目を調整した箇所だけに付ける。構造整理や試験結果だけの箇所には付けない。別ページの指定があればそこで比較できるようにする。

納品・他担当への引き継ぎを頼まれた場合は[引き継ぎ資料](references/handoff.md)を使う。
