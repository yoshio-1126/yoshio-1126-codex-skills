# デザイナー用Figmaスキル（個人版）

## 着手

個人版が選ばれた会話では「見て」「更新した」「納品して」でもこの手順を継続する。初回でも説明や一律の問診を挟まず、指定URLの実データを開く。Figma連携の各操作に必要なスキルを先に読み、その環境で利用可能な読み取り手段を使う。リンクがないときは「確認するFigmaのURLを送ってください」の一問でよい。白紙なら初回点検は保留し、見出し・本文・共通パーツの入った代表画面ができたら共有するよう案内する。権限不足なら何を読めたかと、先へ進むために必要なアクセスだけを伝える。

フレームのURLなら配下と関係する親・正本を確認する。ファイルだけが指定されたら現行の制作ページを特定する。制作ページが複数なら対象を列挙して順に確認し、保管ページ・検証用サンプルを現行画面の件数に混ぜない。既にある仕様とFIX範囲を先に拾い、対象が判断できず結果が変わるときだけ聞く。以前の会話・特定の会社・既定の画面幅を前提にしない。

## 初回から実行する点検

1. [詳細点検の手順](references/deep-review.md) と [共通の検査基準](references/data-checks.md) を読む。選んだ対象の階層を読み、部品の正本・実画面の使用箇所・テキスト・クリップする親・スタイルや変数の参照を取得する。深さ・件数制限のある読み取りは枝ごとに分けて補う。表層のスクリーンショットだけで完了にしない。
2. 実際の表示と設定を突き合わせる。問題候補は、実画面の該当状態、その根拠となる値、最も近い原因まで辿る。同じコンポーネントでも上書きが原因のインスタンスは別に扱う。取得できなかった状態や仮の長文は検証済みに数えない。
3. 「点検・見て」は読み取りだけで完結する。ファイルへのコメント、検証用複製、修正は書き込みとして扱う。初回から細かく調べてよいという指定だけでは編集しない。デザインの良し悪し、使用感、導線設計は講評しない。
4. 返答は「範囲 → 修正判断に必要な事実」。例「商品カード12件を確認しました。2件で説明の最終行が隠れています。本文の高さは自動ですが、外側の枠が64 px固定でクリップしています。」箇所へ飛べるFigmaリンクを付ける。件数・数値は実測したものだけ使う。既知の同じ原因はまとめ、未確認が判断を左右するときだけ末尾に添える。問題ゼロなら一文でよい。

## 制作データの管理

リニューアル案件では、着手時にユーザーへ社内共有の最新版サイトマップの有無と共有場所を確認する。支給済みの版があるときはそれを使う。現行サイトの主要ナビ・フッター・本文からの下層導線も必ず調べ、社内サイトマップ・現行サイト・制作画面を突き合わせる。統合・新設・対象外が不明なページを一覧にして確認する。社内資料が手元にない場合は、ユーザーが指定した正本で照合する。

編集可能なテキストは、役割別のFigmaテキストスタイルで書体・ウェイト・サイズ・字間を管理し、行間は必ず整数％で指定する。混在テキストは範囲別に適用し、共有部品の正本から実画面への反映を検証する。

デザイン上のボタン・テキスト・カードには、実サイトや地図、メール等の実リンクを設定しない。参照元のURLは案件の引き継ぎ先で管理する。

繰り返す構造や共通の操作はコンポーネント化する。テキストだけのリストは、親のオートレイアウトにテキストを直接並べ、項目間をギャップ、外周をパディングで調整する。共通メニューはリスト全体を部品化し、余白確保のための項目ごとの枠は作らない。

色変数は、複数の画面や共通部品で繰り返し使う色に絞り、色名で簡潔に管理する。使用頻度は正本と異なる利用場面で判断する。ロゴ・固有の図版・アウトライン化したタイトルには、共通色と同じ値の箇所も固定色を使う。整理時は塗り・線・文字範囲の実効色と不透明度を保ち、参照がなくなった変数を削除する。

ページの外側フレームはヘッダーからフッターまで全体を収め、内容に合わせて伸ばす。プレビュー用の画面高、クリップ、スクロール固定、開始点や画面遷移は、ユーザーがプレビューを指示したときだけ設定する。作業用の注記は案件の引き継ぎ先に残す。

文字スタイルは見出し・本文・UI・欧文などの役割を先に決めて再利用する。近いサイズや行間の微差で種類が増えそうなら、候補・代表値・影響範囲を示し、統合してよいかユーザーに確認する。承認後は実使用箇所を付け替え、文字の見切れ・改行を確認してから未使用の旧スタイルを整理する。

既存サイトの再設計では公開サイトをクロールし、通常の内部リンクに加え、共通ナビ・フッターの動的読み込み、本文内リンク、タブ、アンカー、同じURLで切り替わる状態を実際に確認する。ページと状態を社内サイトマップ・PC/SPのデザイン双方と照合し、欠落や不明な範囲を確認する。

## 途中確認・修正

次回は、変更した枝とその親、参照する正本、影響を受ける実画面を再読する。変更履歴や前回記録を取得できない場合は対象範囲を再点検する。定期監視を前提にしない。「全体を再確認」なら差分に限定しない。

「直して」「整理して」の範囲内でのみ編集する。事前に元の寸法・正本参照・上書き・既存の操作設定を確認する。正本の変更が指定外・FIX画面に影響する場合は先に範囲を伝え、対象内でできる処置を進める。単純な横組・縦組はその方向のAuto Layout、繰り返す二次元配置はグリッド、強弱をつけた余白は意味のある実要素のネストで扱う。部品の用途をメモし、共通の正本は用途が探せる一つのセクションにまとめる。細部は同梱の共通基準に従う。変更後は対象を再取得し、代表画面の前後・上書き・クリップ・検証用複製の片付けを確認する。

### 「画面全体を整理して」の完了条件

対象の外枠、導入部、各セクション、共通部品を編集前に列挙する。既存の枠がなければ表示内容から単位を拾う。各単位で、デザイナーが次に行う操作（本文を伸ばす、記事を入れ替える、共通のラベルを変える等）を一つ具体化し、基準幅の外観を保ったままその操作ができる構造に直す。文量が変わるときは次のセクションまで追従先を辿る。対象を明示した部分整理では、その範囲に適用する。

Web画面では、編集前に[HTMLの意味構造と読み順](references/data-checks.md#htmlの意味構造と読み順)を確認する。各セクションで見出しが説明する範囲を決め、見出し・本文・下位項目の関係をFigmaの親子関係に反映する。

[整理で使う基準](references/data-checks.md)で全単位を再点検し、[編集操作の試験](references/deep-review.md#整理後の編集操作の試験)を行う。表示、構造、正本・スタイル参照、編集操作の結果を区別する。修正可能な不合格は同じ作業内で直して再試験する。必須の残件や試せなかった操作があれば「一部整理」とし、該当ノードと理由を伝える。

基準幅ごとに[整数寸法の全件検査](references/data-checks.md#整数寸法の全件検査)を最終レイアウトの再取得後に行う。達成数には検査ノード数と小数が残るノード数を含める。

返答は対象へのリンク、確認できた編集操作、主な項目の達成数／対象総数、理由付きの例外・保留・未検証を短く示す。件数には変更前から適合していた箇所も含め、今回の変更数とは区別する。検査記録を残す場合は対象ノードと使用スキルの版（取得できればコミット）を添える。

## 引き継ぎ

納品時は対象画面を通して点検し、[引き継ぎ資料の作り方](references/handoff.md) に従って、①実際の部品を載せたデザイナー用仕様表、②実装担当者用の指示、③新しいチャットでCodexが検索・参照できる案件仕様を作成・更新する。仕様照会は実データとこの案件仕様を照合して答える。データを調べても分からない事項は確定事項と分ける。

## サイトマップと付随画面の確認

サイトマップの作成・更新を依頼されたら、支給図、画面一覧、フォームやCMSの参考画面を突き合わせる。既に指定された画面は再質問しない。図に載りにくい画面や状態（例：フォームの確認・完了・送信失敗、404、一覧の該当なし）について、該当しそうな未決項目だけをまとめて「こちらも制作対象ですか？」と確認する。ページを新設するか、同一画面の状態として扱うかも必要な項目だけ確認する。

返答を待つ間は合意済みの範囲を進める。未決項目を確定ページや制作件数に加えず、回答後にサイトマップと画面一覧を更新する。静的・CMSの区分は資料に従い、一覧と詳細は個別に判定する。
