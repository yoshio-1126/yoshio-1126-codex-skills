# デザイナー用Figmaスキル（個人版）

## 着手

個人版が選ばれた会話では「見て」「更新した」「納品して」でもこの手順を継続する。初回でも説明や一律の問診を挟まず、指定URLの実データを開く。Figma連携の各操作に必要なスキルを先に読み、その環境で利用可能な読み取り手段を使う。リンクがないときは「確認するFigmaのURLを送ってください」の一問でよい。白紙なら初回点検は保留し、見出し・本文・共通パーツの入った代表画面ができたら共有するよう案内する。権限不足なら何を読めたかと、先へ進むために必要なアクセスだけを伝える。

フレームのURLなら配下と関係する親・正本を確認する。ファイルだけが指定されたら現行の制作ページを特定する。制作ページが複数なら対象を列挙して順に確認し、保管ページ・検証用サンプルを現行画面の件数に混ぜない。既にある仕様とFIX範囲を先に拾い、対象が判断できず結果が変わるときだけ聞く。以前の会話・特定の会社・既定の画面幅を前提にしない。

## 初回から実行する点検

1. [詳細点検の手順](references/deep-review.md) と [共通の検査基準](references/data-checks.md) を読む。選んだ対象の階層を読み、部品の正本・実画面の使用箇所・テキスト・クリップする親・スタイルや変数の参照を取得する。深さ・件数制限のある読み取りは枝ごとに分けて補う。表層のスクリーンショットだけで完了にしない。
2. 実際の表示と設定を突き合わせる。問題候補は、実画面の該当状態、その根拠となる値、最も近い原因まで辿る。同じコンポーネントでも上書きが原因のインスタンスは別に扱う。取得できなかった状態や仮の長文は検証済みに数えない。
3. 「点検・見て」は読み取りだけで完結する。ファイルへのコメント、検証用複製、修正は書き込みとして扱う。初回から細かく調べてよいという指定だけでは編集しない。デザインの良し悪し、使用感、導線設計は講評しない。
4. 返答は「範囲 → 修正判断に必要な事実」。例「商品カード12件を確認しました。2件で説明の最終行が隠れています。本文の高さは自動ですが、外側の枠が64 px固定でクリップしています。」箇所へ飛べるFigmaリンクを付ける。件数・数値は実測したものだけ使う。既知の同じ原因はまとめ、未確認が判断を左右するときだけ末尾に添える。問題ゼロなら一文でよい。

## 途中確認・修正

次回は、変更した枝とその親、参照する正本、影響を受ける実画面を再読する。変更履歴や前回記録を取得できない場合は対象範囲を再点検する。定期監視を前提にしない。「全体を再確認」なら差分に限定しない。

「直して」「整理して」の範囲内でのみ編集する。事前に元の寸法・正本参照・上書き・既存の操作設定を確認する。正本の変更が指定外・FIX画面に影響する場合は先に範囲を伝え、対象内でできる処置を進める。単純な横組・縦組はその方向のAuto Layout、繰り返す二次元配置はグリッド、強弱をつけた余白は意味のある実要素のネストで扱う。部品の用途をメモし、共通の正本は用途が探せる一つのセクションにまとめる。細部は同梱の共通基準に従う。変更後は対象を再取得し、代表画面の前後・上書き・クリップ・検証用複製の片付けを確認する。

## 引き継ぎ

納品時は対象画面を通して点検し、[引き継ぎ資料の作り方](references/handoff.md) に従って、①実際の部品を載せたデザイナー用仕様表、②実装担当者用の指示、③新しいチャットでCodexが検索・参照できる案件仕様を作成・更新する。仕様照会は実データとこの案件仕様を照合して答える。データを調べても分からない事項は確定事項と分ける。

## サイトマップと付随画面の確認

サイトマップの作成・更新を依頼されたら、支給図、画面一覧、フォームやCMSの参考画面を突き合わせる。既に指定された画面は再質問しない。図に載りにくい画面や状態（例：フォームの確認・完了・送信失敗、404、一覧の該当なし）について、該当しそうな未決項目だけをまとめて「こちらも制作対象ですか？」と確認する。ページを新設するか、同一画面の状態として扱うかも必要な項目だけ確認する。

返答を待つ間は合意済みの範囲を進める。未決項目を確定ページや制作件数に加えず、回答後にサイトマップと画面一覧を更新する。静的・CMSの区分は資料に従い、一覧と詳細は個別に判定する。
